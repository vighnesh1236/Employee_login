# V_Solutions

V_Solutions is a local employee-management workspace built with React, Express, and Neon PostgreSQL. It keeps employee and operational records in PostgreSQL; browser storage is not used as the system of record.

## Run locally

1. Copy `.env.example` to `.env` and set `DATABASE_URL` to your Neon connection string. Set `JWT_SECRET` to a random secret of at least 32 characters.
2. Install dependencies with `npm install`.
3. Start the API and Vite preview with `npm run dev`.
4. Open [http://127.0.0.1:5173](http://127.0.0.1:5173). The API health check is at [http://127.0.0.1:4000/api/health](http://127.0.0.1:4000/api/health).
5. On first visit, create the super-admin account using the configured `ADMIN_EMAIL`. Choose the password during setup.

The API applies the idempotent schema in `server/schema.sql` at startup. Database connection or schema errors stop the API rather than showing sample records.

## Deploy to Render

1. Push this repository to GitHub and create a new Blueprint in the Render dashboard from the repository's `render.yaml`.
2. Set `DATABASE_URL` to the PostgreSQL connection string in Render's environment settings. Do not commit it or send it in chat.
3. Set `ADMIN_EMAIL` to the email address that will own the super-admin account. `JWT_SECRET` is generated by the Blueprint.
4. Deploy. The Express service serves the built frontend and API on the same origin; `/api/health` is the health check.

The Blueprint uses Render's free web-service plan and does not create a database. Connect a PostgreSQL database you control. Free services can spin down while idle, so the first request after inactivity may take time. The local filesystem is ephemeral on free services: profile photos and locally stored documents may be lost on redeploy or restart. Use Dropbox for documents or upgrade to persistent storage if these uploads must be retained. If Dropbox is enabled, configure its OAuth redirect URI as `https://<your-render-service>.onrender.com/api/dropbox/callback` and add the Dropbox secrets and encryption key in Render's environment settings. The initial super-admin account must be created through the setup screen after deployment.

## Environment variables

See `.env.example` for the required database and session settings. `.env` is ignored by Git. Never commit database credentials or JWT secrets.

`DATABASE_HOST_OVERRIDE` is optional and should normally be left blank. It is only for environments with a local DNS issue; TLS certificate verification still uses the hostname in `DATABASE_URL`.

Administrator setup, sign-in, and employee registration use a generated image CAPTCHA. Each challenge expires after five minutes and can only be used once; refreshing the image or submitting an authentication attempt creates a new challenge. This is a basic anti-automation deterrent, not strong bot protection. Challenges are held in the API process memory, so a multi-instance production deployment should use a shared store such as Redis.

Self-registration supports intern, employee, HR, and manager requests. An optional JPG, PNG, or WebP profile picture can be uploaded during registration; profile images remain private and are limited to 5 MB. All registrations remain pending until approved by a super-admin; the super-admin role cannot be requested or assigned through registration. The super-admin bootstrap is restricted to `ADMIN_EMAIL`, and a database index plus startup check enforce one matching super-admin account.

Employees can link personal Dropbox accounts for document storage. Create a Dropbox app with **App folder** access, add `http://127.0.0.1:4000/api/dropbox/callback` as an OAuth redirect URI, and set `DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, and `DROPBOX_REDIRECT_URI` in `.env`. Generate a 32-byte encryption key with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` and set it as `DROPBOX_TOKEN_ENCRYPTION_KEY`; refresh tokens are encrypted at rest. Documents use Dropbox after an employee connects their account, or private local storage if they have not connected. Profile photos stay in private local storage so they can be uploaded during registration before Dropbox is linked.

## Implemented workflows

- One-time super-admin setup, secure password hashing, HttpOnly session cookie, and role-checked API routes.
- Employee registration, pending approval, and super-admin approval or rejection.
- Super-admin-only attendance recording and salary adjustments; employees, HR, and managers can view their own read-only attendance and salary information (managers can also view their team attendance). Leave attendance is categorized as medical, casual, or unpaid.
- A read-only holiday calendar for 2020–2100 marks every Saturday and Sunday and lists India-wide fixed-date holidays, configured festival dates, and state-level public observances. Regional observances can vary.
- Month-filtered attendance history and monthly salary records.
- Monthly salary record generation for admin review, admin-edited draft salary records, manual payment status, employee salary history, and performance reviews. Attendance and performance metrics are visible during manual review; no automatic pay formula is applied.
- Employee-to-super-admin private messages, leave requests, and approval/rejection responses. Employees can save their UPI ID; only the super admin sees it in payroll review.
- Private, permission-checked local document upload/download/delete and role-filtered notifications.
- Responsive dashboards and database-derived metrics.

## Local-development scope

Local uploads and profile photos are stored under the local `uploads/` directory and profile references persist across sign-out. On Render's free service, this local storage is ephemeral and files are not guaranteed to survive deploys or restarts. Dropbox OAuth requires an app configuration for the deployment. Email-based password reset, PDF/Excel report exports, automated unpaid-leave proration, and full administrative policy/role assignment screens require additional service credentials or implementation before this can be considered production-ready. No payment is ever transferred by this application.

Use a private Neon project and rotate any credential that has been shared in chat before exposing the service publicly.
